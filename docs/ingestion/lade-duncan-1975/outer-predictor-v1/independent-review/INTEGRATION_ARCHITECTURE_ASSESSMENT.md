# Source-only versioned generic implicit-path integration assessment

Decision: the proposed architecture can satisfy normal generic-engine delivery. It is not intrinsically a model-specific handwritten kernel or a separate model website. Acceptance is conditional on implementing the versioned generic runtime as a maintained public profile, normal compiler regeneration, explicit routing/guards and actual package/browser qualification. This assessment approves neither E5 nor integration, and cannot pre-approve unobserved full campaigns.

A generic engine does not have to be one unversioned shared binary. Keeping the qualified generic runtime as an immutable versioned profile avoids replacing concurrent Duncan/common repairs. Its generated four-model corpus, generic residual evaluation, generic implicit/path controller and common C ABI can remain byte-identical. Exposing only the independently approved Lade record through the existing main-laboratory controller router is compatible with the checklist. Do not copy the frozen solver over the current shared solver, present this as qualification of current shared runtime, or expose the other three regression witnesses as approved models by accident.

Required guards and provenance:

1. Canonical definition: install exact Lade JSON bytes SHA120b93f319543518b2b87221ab7457afaca2a1fb5de78af901276e8e89a22e63 at the separately reviewed canonical path. Approval registry, evidence index, dossier, examples, catalogue entry and download links must bind that path and hash, preserving the exact id. Do not rename metadata or reserialize the definition. Canonical public discovery and model-count manifests include Lade once. The three witnesses stay separately identified build inputs; do not overwrite their current canonical models with historical copies.
2. Compiler/build: pin ordered four-input paths and individual hashes, normal schema/compiler/dependency version and invocation, byte-identical generated header AND full compiled catalogue, exact generic runtime/header/main/CMake/build options/toolchain/link inputs, and qualified native/Wasm/loader hashes. The existing current-generator-probe saved outputs match the qualified header/catalogue byte-for-byte; this establishes observed compatibility, not permanent compatibility with future compiler changes. Reproduce and retain the canonical-path regeneration at integration, not just a report saying it was possible. Any generated/runtime/compiler-output difference requires impact review and appropriate requalification.
3. Artifact reuse: package the exact qualified bytes under a versioned profile namespace. Keep the profile build recipe, generic regression corpus and ownership in the repository; archived artifacts alone do not turn a research executable into a maintained public engine. Content-addressed names or an immutable manifest should bind loader, Wasm, compiled catalogue and profile source receipt. Loader locateFile must select the matching Wasm asset under the deployed project path. Verify fetched bytes or a trustworthy packaged-integrity chain, not filename resemblance. Do not rebuild merely to change an artifact basename unless the rebuilt artifact is qualified.
4. Catalogue routing: preserve the four-model engine catalogue's own sha256 and full parameter/state ordering. `atlas_describe` must match that exact complete catalogue; each response must return its engine catalogue identity, requested exact model id, settings, parameters, initial state, controls and declared stress scope. The public discovery catalogue is a different object; do not truncate the compiled catalogue to one model, replace its hash with a merged public catalogue hash, or send the current ordinary engine's hash to this profile. An explicit route manifest maps the one public Lade id/definition hash to this profile/catalogue/artifact identity and rejects unknown/duplicate/stale mappings. No fallback to an ordinary engine after a mismatch.
5. Witness isolation: discovery, examples, model selectors and supported-controller routing expose only the approved Lade entry from this bundle. Keep witnesses in atlas_describe for identity checking; the route/controller allowlist rejects attempts to select them through this public profile. This is a product scope guard, not a claim that a downloadable four-model Wasm module cannot be called directly.
6. Browser contract: implement a reviewed profile-specific eight-setting serializer/validator and returned-settings verifier with frozen names, ordering, types, version/norm and defaults. The current web/numerics.mjs only supports six settings and rejects unknown keys; current laboratory-scope.mjs delegates to that validator and assumes its catalogue. Merely adding Lade to current models.json will fail or silently lose the required profile. Keep current six-setting behavior intact. Expose only qualified protocols/loading/settings/parameter-initial scopes with explicit total mechanical stress, zero-pore embedding and unavailable reconstructed pore pressure; never use the legacy implicit-effective route for this model. Custom controls require their actual ABI and backend/browser evidence; the bounded worker's three allowed APIs do not currently qualify every exported API.
7. Transaction/UI lifecycle: use the main-laboratory router and a dedicated cancellable worker or equivalent isolated owner, with latest-request sequence guards and reset/import/model-switch cancellation. A synchronous Wasm ccall on the main UI thread is unacceptable for a ~104-second run. Browser deadline includes module fetch/init and execution, terminates only its owned worker at the declared cap, retains explicit failed/committed-prefix semantics and permits recovery. Node spawnSync evidence is backend evidence, not proof of browser cancellation. Preserve the qualified stress/shear/unit conventions, hidden numerical q carrier versus decoded physical H meaning, and clear numerical/domain limitation messages in view/export/replay.

Numerical campaign reuse boundary: if canonical-path normal generation is byte-identical, the same qualified runtime/artifacts are served, all requested numerical inputs are identical and the wrapper only transports/validates/renders, the complete scientific source/refinement/domain/native/Wasm campaigns do not need repetition solely because assets moved into a public profile directory. This requires their eventual complete PASS on the exact current runtime; the hardcase prerequisites alone are insufficient. The new router, manifest, eight-setting codec, worker lifecycle, defaults/examples/import/export and packaged assets DO need focused integration tests and actual browser E7 qualification. Run existing package/default gates with this model visible, preserve failures and verify current unrelated Duncan/common routes. Compare browser-captured numerical requests/responses with qualified fixtures, including zero/invalid/reset/recovery/latest-request cases and fetched identities. This is targeted integration qualification, not a waiver of numerical gates.

Blockers before E6 completion: complete current numerical campaigns and independent nine-item E5 approval; reviewed canonical/profile/manifest changes and build-generation receipt; actual eight-setting total-scope worker/controller route; package/default/browser qualification and public witness isolation. E8 still requires separately authorized publishing and verified live assets/run. A static specialist page or hidden standalone executable does not close these stages.

Alternative: merge the generic capabilities into the concurrently maintained common engine under separate ownership and requalify that changed engine. That is legitimate but not required merely to avoid runtime versioning, and it is a broader numerical change. The versioned generic profile is the smaller evidence-preserving route if the project accepts its maintenance and manifest obligations.
